# Implementation

*Where each part of the model lives in this repository's code, and which tests and harness rows hold it.*

## What this is

The map of the repository is [`../CLAUDE.md`](../CLAUDE.md): what each file is and what it owns. It stays the authority on that, and nothing here repeats it. This file adds what the map does not carry: a crosswalk from the model to the code. A reader of [`model/fill.md`](model/fill.md) who needs to find the fill's bake, the reference it is held to and the harness row that would go red comes here. It also keeps the implementation facts the model's meaning does not depend on: texture formats and why they were chosen, the uniform budget, the per-frame signatures that decide a re-bake, the floating-point traps the code was built around, the harness and its commands, and how a bundle is cut. Everything here describes the code as the old spec and the map record it. Where the two disagree, or a name could not be confirmed, an `AUDIT` comment says so. Where a fact belongs to the model, this file gives it one sentence and a link.

## The engine's shape

**One door.** The renderer is a standalone ES module. `komorebi.js` is the public door: it re-exports the modules under `engine/` and has no UI of its own. Its surface is `export { create, DEFAULTS, MAX_LAYERS, MAX_SAMPLES, DEG }`. It also exports a few couplings for one reason only, so that a test can read them. Without that, a disagreement between them would fail silently:

- the transition key sets `MORPH_KEYS`, `CANOPY_KEYS`, `TOPO_KEYS` and `MODE_KEYS`, which let a test assert that every knob is classified;
- the camera registry's `CAMERAS`, `TRANSPORT_GROUPS` and `GROUP_UPLOAD_KEYS`, which let a test assert that its three halves name the same groups.

**Where the modules sit.** The engine's modules are under `engine/`: `komorebi-engine.js`, the parameter registry, the session profiles, the shared maths and the editor-only tools at its top, and the rest in a folder named for the model file that owns the mechanism (`light/`, `canopy/`, `leaf/`, `season/`, `motion/`, `transport/`, `transitions/`). The editor's modules are under `editor/`. `komorebi.js`, `presets.js` and `macros.js` stay at the root beside the pages, so the address a page imports does not move. The map names every file.

**The subsystem factories.** `komorebi-engine.js` is `create()` itself. It holds the GL plumbing, the shared-internals hub, the rebuild coordinators, auto-quality and the frame loop. Each subsystem is a factory module that closes over the hub: the grove (`komorebi-grove.js`), the bake and the sky fill (`komorebi-bake.js`), the source (`komorebi-source.js`), the cast geometry (`komorebi-cast.js`), the motion (`komorebi-motion.js`), the litter (`komorebi-litter.js`), the tree view (`komorebi-tree-view.js`), the transitions (`komorebi-transitions.js`, which picks the route between two looks and runs every long route's lifecycle), the five modules that each hold one long route and return its entry (`komorebi-scene-fade.js`, `komorebi-leaf-travel.js`, `komorebi-season-travel.js`, `komorebi-grove-travel.js`, `komorebi-litter-rise.js`; see [Transitions as a registry](#transitions-as-a-registry)), the render (`komorebi-render.js`) and the editor tools (`komorebi-editor-tools.js`). They stand on four foundations: shaders (`komorebi-shaders.js`), transport (`komorebi-transport.js`), params (`komorebi-params.js`) and the shared math (`komorebi-math.js`: constants, interpolation, the RNG). The routes stand on one more, pure: what a route is (`komorebi-routes.js`). The laws live in pure modules, with no GL, so a unit test can run them without a GPU: the season (`komorebi-season.js`), the light (`komorebi-light.js`), the camera (`komorebi-camera.js`), the skeleton grammar (`komorebi-grammar.js`), the air (`komorebi-air.js`), the leaf's outline, material and side (`komorebi-leaf.js`), the fill's quadrature (`komorebi-fill.js`), the litter's laws (`komorebi-litter.js`), the shoots (`komorebi-shoots.js`) and the year-by-year growth (`komorebi-growth.js`). See the map for each module's ownership.

**The handle.** `create(canvas, { params })` returns a handle:

| Member | What it does |
|---|---|
| `apply(scope)` | re-applies the current params at a named scope (`'season'` and `'density'` take the cheap paths of [`model/season.md`](model/season.md)) |
| `setParams(p)` | assigns params |
| `transitionTo(params, { duration, onEnd })` | moves to another look by the route [`model/transitions.md`](model/transitions.md) selects |
| `setPaused(b)` | stops or resumes the loop |
| `dispose()` | stops the loop and frees every GL object and the context, so a second, disposable engine can be reclaimed |
| `params`, `perf`, `motion`, `src`, `trans` | live state |
| `onFrame` | a per-frame hook |

The engine runs its own `requestAnimationFrame` loop on the canvas it is handed. `create()` throws when WebGL2 or float render targets are missing, so a page can fall back to a static picture.

**Looks are data.** The built-in looks live in `presets.js` (`export const PRESETS`). Each is merged over the engine's `DEFAULTS`. The editor reaches them only through the shipped playlists beside them (`PLAYLISTS`), which set the order they are walked in and how long each is held; `EXPERIMENTAL` names the looks still finding their feet, which are their own playlist and stay out of the player bundle. `DEFAULTS` is the merge base. It is exported, but it is not itself a look. Each look's intent is recorded in [`contracts/looks.md`](contracts/looks.md).

**Every parameter is defined once.** `PARAMS` in `komorebi-params.js` is the registry: one entry for each parameter komorebi has, with its default, its row in the editor's panel (kind, label, range or choices, what a change rebuilds) or the reason it has none, how a transition carries it (`travels`), whether it wraps, its older names, and what it means in the editor's hover. `DEFAULTS`, the key classes and `LEGACY_KEYS` are derived from it; the editor builds its panel rows and hover texts from it, keeping only where each row sits and when it shows; the tools that hold a saved look to the editor's ranges read it. Two editor inputs a look does not store (`time_of_day`, `latitude`) are in it as inputs, with no default. `params.test.js` guards it: every parameter means something, travels some way and has a row or a reason, and the panel names every row once. It also holds what a row rebuilds to what reads its key. Growing the grove is the dearest scope, on every tick of a drag, so a row asks for it exactly when the grove's build reads the key (`GROVE_READS`): the leaf's rim (`edge_softness`) asks for the bake alone, the wood's opacity and radius for nothing, the season set for the re-season, and the rows that choose the cast for the textures. The exceptions are named in the test: the canopy's two heights and the wood's radius, which `refreshWood` re-reads from the grown skeleton with the frame; the two texture sizes, which are choices and regrow once a click; and the view's extent, which only a look that names no reach reads, at a build: a zoom is no build, and the engine names the reach before the next one. The bundles drop the editor's fields (`row`, `noRow`, `means`; `embed-build.mjs`), so a page pays for none of it.

**Old spellings keep working.** One alias map, `LEGACY_KEYS` (derived in `komorebi-params.js` from each parameter's older names, beside `migrateLegacy`, re-exported through `komorebi.js`), translates retired param names to current ones. It is applied at every door external params come through: `create`, `setParams`, `transitionTo` and the ★ store. A current name that is already present wins, and nothing the engine writes back out uses an old name. `legacy-keys.test.js` is the test for it by name.

**The consumers.**

- **The editor.** `index.html` is a thin shell over `editor/editor.js`: the dev panel, the insets, preset management, sun-drag and scene stepping. Its pure parts have their own tests:
  - `playlists.js`, `arboretum.js` and `arboretum-api.js`: look storage and arboretum;
  - `macros.js`: the control bus (`createBus`);
  - `leaf-maze.js` and `leaf-preview.js`: the held leaf.
- **The player.** `player.html` is a viewer-only reference: a full-bleed canvas that cycles through looks with `transitionTo`.
- **The global shim.** `komorebi.global.js` bundles the engine and the looks into a classic `window.Komorebi` global, for pages with no build step.
- **The bundles.** `embed-build.mjs` writes `dist/komorebi.player.min.js` (every shipped look) and `dist/komorebi.embed.min.js` (only the looks one page names). See [Build and bundles](#build-and-bundles).
- **The examples.** `examples/` holds the embeds the README points to.

Pages that import the modules natively must be served over http(s), not opened from the filesystem (`nix run .#dev`).

**What the editor tier adds.** The engine carries an `EDITOR` constant. In the editor build the handle also has a small `profiler` (GPU timer-query instrumentation, which `nix run .#cost` reads) and a motion mirror (`setMotionSource`, which copies the live motion and spring state into a second engine each frame, for the test tools that drive two). These sit in `komorebi-editor-tools.js` with the debug overlays. The bundles fold the tier off (see below). The general `setPaused` and `dispose()` ship everywhere: a page may create and dispose engines as it likes. The held-leaf inset, the playlists and arboretum are imported by `editor.js` alone. No engine module, preset or bundle names them: `maze.test.js` and `arboretum.test.js` hold that.

## Transport as a registry

The model fact is [`model/transport.md`](model/transport.md#one-program-per-camera): one program per camera, chosen at compile time. This section covers how that is built.

**A camera is a compiled program.** Transport lives as named GLSL snippets in `komorebi-transport.js`: camera blocks, occluder tiers, materials and the shared Look tail. Each snippet carries its own uniform declarations, and `buildTransport()` assembles them. A camera can only change through a structural rebuild, so the selection is a build key, not a runtime branch. Within a variant every emitted line is a line the single shader used to run. The branches disappear because they are left out, and the two flags that once chose between them do not reach any variant. The cameras are:

- floor;
- cloth (the curtain);
- enclosure (the tent);
- sky (the retina);
- a transition-only viewpoint that joins sky rays to floor casts. Bundles keep it only when they keep both the sky and floor cameras.

**Three halves that must agree.** One entry per camera is read by three consumers:

1. **the assembler**, which picks the snippet composition and declares the groups' uniforms;
2. **the location table**, which looks up the uniform locations each group names;
3. **the per-frame upload**, which fills each group (`GROUP_UPLOAD`, keyed by `GROUP_UPLOAD_KEYS`, called from `komorebi-render.js`'s per-group upload).

Each uniform group names its GLSL declarations, its location keys and its upload together. A uniform declared in one variant but filled in another therefore shows up as a key that does not line up, rather than as a silent black frame. `registry.test.js` holds the three halves to the same groups. It also holds the shared sky ray to one exact text in both the sky program and the fill program, and holds that snippet never to read `uAmbient`. What a new entry owes is the extension contract in [`contracts/gates-and-rungs.md`](contracts/gates-and-rungs.md). Materials ride the camera because every receiver so far has exactly one.

**Why the split: the uniform-row budget.** The split buys headroom, not speed. The four-in-one shader declared **246 vec4 rows** of uniforms against WebGL2's guaranteed **224**. Split, each camera declares only what it reads. One more thing moved out of the uniforms: the occluder's segment table, two vec4 arrays that, at the table's original 64-segment capacity, would have cost **128 rows** in every camera at once (the table is now 256 segments). With it gone, the four variants stand at **85, 94, 101 and 30** rows, all well inside the floor.

**The segment table as a data texture.** The analytic woody occluder is a fixed table of segments, its capacity `MAX_OCC` = 256 in `komorebi-params.js`: one row of plan endpoints and one row of heights.
It is stored as an RGBA32F data texture that the shader reads with `texelFetch`. That read is exact on RGBA32F, so it carries the same floats a uniform upload did. A marginal tree's coverage is stored beside each segment's radius, so a tree-count morph fades the whole tree's wood. The texture can hold two sets, which is what a wood crossfade would need (not built; see [`exploration/open.md`](exploration/open.md)).

**One compile per camera, for the engine's life.** Each program is compiled on the first use of its camera and kept. The one compile a camera ever costs lands inside the rebuild a mode flip already performs.

**One link per program, for the context's life.** A program belongs to the GL context that linked it, and a driven scene (the scene dissolve's outgoing look, the litter rise's source, grove travel's other end) draws on its host's canvas, so on its context. The engine's own programs (its bakes, its blits, every camera it visits, the fill's and the litter's) therefore come from a table kept per context and keyed by their two sources: a scene takes what its host has already linked instead of linking it again. Each program is counted once by each engine holding it, however often that engine asks for it, and deleted when the last engine lets go; a lost context forgets the whole table. Sharing a program shares its uniform values, which is sound because every draw uploads each uniform its program reads before it draws. Every route takes its own programs (the dissolve's mix, the travel casts, leaf travel's progress and blur passes, the litter rise's flights) from the same table, through the host engine, and deletes none: only an engine's first run of each route links them, and they go with the engine. Grove travel's wood pass is the engine's own faithful wood program. The ledger suite holds every route, run a second time, to linking none of its programs. Linking was most of the frame a dissolve froze on (see [`evidence/measurements.md`](evidence/measurements.md#the-dissolves-first-frame)); the transition-routing suite holds a dissolve to the one program it links, its mix. A season travel's snapshot copies what the re-season has just written from the re-season's own record instead of reading the faithful buffer back, which would wait for the GPU to finish the frame before. Leaf travel, grove travel and the litter rise read a layered grove's leaves from its record the same way (`readFaith` in `komorebi-grove.js`); only a faithful grove's are read back from its buffer. `glslcheck.mjs` assembles every GLSL template literal and compiles it with `glslangValidator`, so a shader typo fails offline instead of as a black canvas.

The program linker disposes of intermediate shaders after each link attempt. The editor profiler releases pending timer queries when instrumentation stops or the engine is disposed.

## Transitions as a registry

The routes and what each promises are [`model/transitions.md`](model/transitions.md) and [`contracts/transitions.md`](contracts/transitions.md). This section covers how the long routes are held, on the model of the camera registry above: a route is an entry, and nothing outside the entry and the chooser learns its name.

**A route is an entry.** Each long route's module (the scene dissolve, leaf travel, season travel, the litter and shadow flights, grove regrouping) returns one object built over the engine's hub: its `name`, and `begin`, `retarget`, `step(dt, t, e)`, `draw`, `finish` and `end`. `begin` prepares the route from the look on screen and may decline; `retarget` takes a selection made while it runs, reversing toward one of its ends or keeping it pending for the landing; `step` is one frame, and returning false gives the route up; `finish` puts the landed look in place and hands back what it kept pending; `end` releases everything the route holds, and is safe while idle and twice. The scene dissolve has neither `retarget` (a selection made during it waits or takes another route) nor `finish`. The engine keeps the five as `hub.routes`, and `trans.route` is the one running, or null; it is the only record of which route runs. A bundle that cuts a route keeps an entry with its name and an `end` that does nothing (`cutRoute`), cut with the route's gate, so nothing else of it is reached. The entry's shape is written down in `komorebi-routes.js`; `routes.test.js` holds every entry to it, in the raw modules and in a bundle that cuts three.

**Policy is declared, not special-cased.** What differs between routes in how they are run is a field of the entry, read by the lifecycle:

- `ownsWind`: the route advances the wind itself, so the frame does not tick it (grove regrouping, which advances both ends' wind);
- `hostBakes`: the host's canopy is baked under the route on a moving frame (the scene dissolve, whose incoming look is the engine);
- `tweens`: the look's live keys morph under the route, so its step runs after the morph, and at landing the live look is set to the target before `finish` (season and leaf travel); the others step in place of the morph;
- `keepsDrift`: the morph and that landing leave `drift_phase` to the wind while `drift_auto` (season and leaf travel);
- `groundPeak`: the ground's brightest channel moves straight between the ends' while the hue tweens (leaf travel's one field of dapples);
- `swaps`: the route lands showing the target's own picture, `trans.swapped` true (the dissolve and the two carrying routes);
- `landing`: the hub's coordinators run, in order, once the route is ended (the source and the bake the landed look needs; the adaptive clock resuming).

**One lifecycle.** `makeTransitions` (`komorebi-transitions.js`) returns everything the engine needs, and the engine names no route: the frame asks the running entry whether it owns the wind and whether the host bakes under it, and draws with its `draw`.

- *Start.* A route started from idle starts from rest: every field of the transition state is put back first, so nothing a route before it left is read. An interruption reads what is shown before anything changes. The two routes that carry their own leaves (grove regrouping, the flights) start through one helper once their `begin` has prepared them. When the chosen route is not the one running, the running one is ended.
- *Tick.* The clock, the moon and the layer heights, the viewpoint's eye, the carried bloom and the shadow opacity, then the running route: one that does not tween steps in place of the morph, one that tweens steps after it. Started from rest, the two carrying routes carry no bloom and no shadow fade, so they share the dissolve's stage.
- *Land.* One function for every route, in the order above. Landing does not return the state to rest: the clock, the swap, the bloom and the opacities stay what the last frame showed. A waiting selection still beats the route's pending one. A route that gives up mid-flight (leaf travel, when the actual correspondence is over budget) lands as a scene dissolve to the same target, from rest, keeping the caller's clock and completion.
- *Abort* (a hard swap of the look): the running route is ended, a half-faded incoming grove freed, and the state returned to rest.
- *Context loss and restore.* The loss ends every route and leaves none running; what is owed, a route's pending selection or a waiting one with its completion, survives. The restore lands on it from rest.
- *Dispose.* Every route is ended.
- *One bake per picture.* A bake that is overwritten before anything reads it is not made. A driven scene (the dissolve's outgoing look, the litter rise's source, grove travel's other end) is baked once, after it copies its host's motion; a landing that copies motion from the scene it leaves rebuilds without a bake and lets the landing's own bake be the one; a faithful grove morph's last frame skips the morph's bake, since the landing bakes the exact target over it in the same frame. The ledger suite counts these bakes.

**The state at rest.** `restTrans()` gives every field of the transition state, grouped by what it is (the clock and its bookkeeping, the running route, the litter flight's flavour, and the modifiers of the live morph: bloom, crossfade, canopy morph, the lit-ground fade, wood, the diffuse split, viewpoint, window, seen tree, iris, moon, layer heights), each at the value under which every reader behaves as if no route ran. Only the caller's duration is carried across a start, an abort or a restore: it is the sticky default for a later call without one. Every hub that holds a transition state starts from it: the engine, each scene a route borrows, leaf travel's outgoing scene and season travel's cast.

**A draw mode is not a route.** The draw modifiers `komorebi-render.js` and `komorebi-tree-view.js` read off a scene's state are fields of it, not route names: `travelField` and `travelTone` (a moving cast's transmission map and the tone weights a moving picture is finished with), `riseField` (the flights' eye targets), and `castHeld`, set while a route holds the faithful cast, so the frame neither refreshes it nor stands it up as the seen tree: season travel on its own engine, grove regrouping on its carrier scene.

**Where the chooser lives, and why.** Which route a pair takes stays in `transitionTo`, the one place that names a route. Leaf travel and the scene dissolve are gated on the classification's own products (the morph's cost, the mode and topology differences, a moon in flight), and those gates are the spec's own order of routes, so the chooser is written as that order rather than as a predicate per entry. The pure eligibility predicates stay with their routes' modules.

## The crosswalk

One table per model file. *Module* names the file that owns the mechanism (see the map). *Named* lists the function or constant the old spec names. *Unit* lists the bun tests (`*.test.js` in `test/`). *Harness* lists the pixel-harness suites and flags and the `test-gl/*.mjs` route drivers. "Not recorded" means the old spec does not say. Test files whose contents the old spec never describes are listed by name only.

*Representation.*

- **The outline texture** is **256 × 64 R16F** (32 KB). One species takes eight rows, one per outline variant. With `leaf_variety`, a genotype grows eight outlines, one per light class, so the texture holds 64 rows, row = g·8 + c.
- **The id packing.** The row rides in the fraction of the cluster id. An eight-row grove packs it as **j + variant/32**, exact in float32 for any cluster below 2¹⁷. A varied grove packs its first column and the blend toward the next as **j + (row₀ + 0.1 + 0.8·w)/128**: the 0.1 margins keep a float's error from crossing a row, which holds while a float32's half-ulp at j is under 0.1/128, so for any cluster below 2¹⁴; there the blend is good to under 0.08 of a column. The GPU's `MAX_TEXTURE_SIZE` caps the clusters (2¹⁴ on most devices, so inside the bound; 2¹⁵ on desktop GL, where a varied grove past 2¹⁴ clusters can read a neighbouring row), and the engine does not cap it further. A design that packed with 512 was exact only to 2¹⁵. The litter keeps the row the leaf hung in, in instance slot 7, instead of rehashing it.
- **The vertex and fragment sides differ on purpose.** `VS_BAKE` and `VS_FAITH` read the packing through a uniform: rounded to a row, `floor(fract(iC.w)*uLeafIdFrac + 0.5)`, and raw in a varied grove (`uLeafIdFrac` 128), whose fraction is the blend `leafQ` mixes the two rows by. The fragment side keeps a literal `/8.0` and overrides it in a uniform branch for a varied grove only; [Numerical discipline](#numerical-discipline) says why.
- **The texel law** is stored as nothing new. Every reader reconstructs the mixture from the same two numbers in the layer texel.

*Representation.*

- **The carpet** is one **RGBA8** texture over the fill's frame. RGBA8 because linear reflectance is LDR. It is **premultiplied**, blended `ONE, ONE_MINUS_SRC_ALPHA`, so alpha accumulates as `1 − Π(1 − a)` where straight alpha would square it. Premultiplying also lets the bilinear read and the mips average coverage-weighted colour, instead of darkening every edge toward the empty texels' black. It is mipped, so the far floor of a tilted camera reads a mip rather than a shimmer of single texels.
- **Small leaves.** A leaf smaller than a texel is drawn at three quarters of a texel's half-extent, and its alpha is reduced for the area it gained.
- **Cost of the format.** Quantisation is coarse in a wet brown's blue (about 7/255), but the value is constant per leaf, so it does not band.
- **When it is allocated.** The texture is 1×1 until a leaf has fallen on a floor that asked for litter, with no program, no buffer and no pass. `litter_resolution` (default 1024) is a TOPO-class tune knob. Memory per size goes to [`evidence/measurements.md#season`](evidence/measurements.md#season).
- **What the re-season record survives.** The engine re-seasons only while the grove's key still matches, no transition is in flight other than a season-only grove morph, and the grove is the one attached to the engine (below, "One grove attached at a time"). Otherwise the next `'season'` apply is one full build that keeps a record, and the one after is fast. The record is lazy: a summer build keeps none (recording costs about 5 ms and 7 MB a regrow), and the build keeps one only when the structure it grows is the one on screen, so the spring half of the season macro, which moves structure every tick, does not record and discard one per tick. The exposure field and its rank come from the build when it ran the exposure pass, otherwise from the first re-season whose gate needs `u`, and the cached rank is never written into. A and B₀ are kept as doubles, since the litter's sizes are read from the doubles and a float32 copy differs in the last bits. `hier.leafW` is a new array on every re-season, because the tree inset keys on it. The record keeps each leaf's draws (`season.draws`, four doubles) and its schedule (`season.sched`, eight doubles and the drop day, keyed on `SCHEDULE_KEYS`: the season set without `phenology`, `trans_rgb` and `wall_fraction`, plus `drop_after_turn`); the exposure blend `u` is read only when the schedule is rebuilt. `grove.litter` after a re-season is a getter that builds the list on first read and keeps it; assigning to it replaces it with a plain list, and `refreshLitter` reads it only when the floor wants a carpet. A `'season'` apply bakes only when no frame will (`frameBakes`): with the loop running, the canopy moving and no transition in flight, the next frame's own bake is the one that shows the step, so the apply's would be thrown away.
- **The reach.** `buildGrove` fills `grove_reach_m`, or the view's extent where the look names none (0), and keeps what it used on the grove (`grove.reach`). `holdReach` in `komorebi-engine.js` names the reach for the look once the view differs from it: asked at every `apply` and whenever the look is read back (`captureLook`), never while a route runs, so the wheel and a pinch, which write the view and ask for nothing, are caught at the next edit or save. The key is in no transition class: 0 and the view it stands for are one grove, so where either names one `transitionTo` compares the span each end's trees are grown across (`groveFill` in `komorebi-grove.js`: the reach, at least 0.5 m and capped at 0.46 of `canopy_extent_m`, the one rule the build itself spaces trees by), and the season travel admits a reach that differs past that cap; a grove morph tweens the reach (`trans.reach`) and lands on the target's own value. Past the cap a reach moves nothing: the park story's standing looks name 13.5 to 39.3 m over a 3.0 m cap and grow one grove, which the camera alone moves between. The grove macro's stops name the reach their view had. `reach.test.js` holds all of it, and the harness a zoom under a named reach.
- **The build in two halves.** `buildGrove` is `growGrove` then `uploadGrove`, then the attach. Growing is the arithmetic: it reads the params and returns plain data (the hierarchy, each layer's leaves and the faithful leaves as the arrays the GPU takes, the pivot weights, the wood's tables, the cast frame's box, the season record), and touches neither the GPU nor `faith.*`, `occ.*` and `sky.*`. Uploading makes the vertex arrays and textures from that data and returns a detached grove that holds its own state, reading nothing but what it was handed, so the live params may be another look's by then; a density capacity re-seasons at the upload under a copy of the params it was grown under. Only a grove grown faithful (the key's own bit, `faithfulOn()`) puts its faithful leaves on the GPU there. A layered grove never draws them, so it keeps them as a record on the CPU (`faith.rec`: the leaves, their pivot weights and their sides, as a buffer would hold them): its re-season rewrites the record instead of a buffer, the routes read it, and the bake asks `faithGL` before it casts, which uploads the record and lets it go should a layered grove ever be cast faithfully (no look or route does today: every faithful cast is of a grove grown for it). A layered regrow and re-season send the GPU their layers alone, about half the bytes (see [`evidence/measurements.md`](evidence/measurements.md#a-layered-groves-faithful-leaves)). Neither half frees anything: the grove a build replaces is freed whole by `installGrove`. A regrow takes that grove's GL objects instead of making its own: `buildGrove` hands the grove it detaches to `uploadGrove`, which re-specifies each of its buffers under the buffer's own name (so a vertex array kept with it keeps its pointers), rewrites a data texture of the same width, keeps the outline's texture as it is when the outline is the same (outlines are memoised), and leaves whatever it did not take on the old grove for its free. The grove value is still new per regrow, so the carpet, the tree preview and the tests that ask whether the grove regrew read it as before. A grove morph regrows every frame with one layout, so its frames make no buffer, vertex array or texture (`gl-ledger.test.js` counts them; see [`evidence/measurements.md`](evidence/measurements.md#the-regrow-in-place)). Season travel points a seventh attribute of the faithful vertex array at its own buffer, and turns it off when it ends, since the vertex array outlives it. The crossfade's incoming grove is grown and uploaded without the attach (`buildTargetGrove`), so the grove on screen keeps its state on the engine until the window closes. `grove-build.test.js` holds both properties on a GL that counts its calls, that the halves and the attach give the grove one build gives, and that a layered grove uploads no faithful buffer until a cast asks, once, while a faithful one uploads its own.
- **One grove attached at a time.** A grove owns its state: its GL objects and hierarchy, and `g.own`, the faithful leaves and wood with their counts and bounds (`faith`), the analytic wood's table (`occ`) and the sky view's binned wood (`sky`). The engine's `faith`, `occ` and `sky` objects keep their identity for its life, because the bake, the render, the tree view and the routes destructure them, so a grove is read by being attached: `attachGrove` moves its state onto them, `detachGrove` moves it back with whatever changed meanwhile and clears them, and `freeGrove` frees every GL object the grove owns, detaching it first. These three are the only code that knows which fields are a grove's (the keys `uploadGrove` gave `g.own`); the rest of the three objects is the bake's (the cast frame and what the cast was baked with, the per-sample scratch, the occluder's per-frame table, `sky.branchTau`). Every hand-over in the engine is made of them and `setViews`, which points `grove`, `hier`, `layerVAO` and the cluster textures at a grove or clears them: installing, a dissolve's scene adopting the host's grove (and the litter ascent's source, which is the look on screen too), the host adopting the grove of the scene it lands on (grove travel's other end, the litter descent's floor: the scene grew that look's grove, so the landing does not grow it again), the leaf travel's outgoing scene borrowing it and giving it back with the whole texture set and its sizes, dispose (the grove on screen and a crossfade's incoming one), and a restored context, which detaches the grove and frees nothing, its handles being dead. A host whose grove was taken keeps its `hier`: its regrow carries the springs from it. A grove's vertex arrays read the quad buffer of the engine that uploaded them, so a driven scene draws from its host's quad buffer and leaves it alive when it is released. `gl-ledger.test.js` drives every route on a GL that keeps a ledger of what is alive, and holds that nothing is used after its deletion or deleted twice, and that a disposed engine leaves nothing alive.
- **What a regrow pays for.** A grove's build draws nothing it has drawn before under the same seed. A cluster's arrangement and wind streams depend on the seed and the cluster alone, and the hang loop takes them in one fixed order, so `makeGrove` keeps each cluster's draws (its two wind draws, and per leaf two gaussians, seven arrangement draws and two wind draws) and grows the kept run when a build wants more leaves. It starts over when the seed changes. The leaf records are written by index into typed runs of doubles and rounded to float32 only at upload, as the arrays they replaced were. Every pass that reads them back sees the same doubles, so the uploads are byte-identical. A grove morph regrows every frame, and at 30 k leaves a regrow now costs about 6 ms (see [`evidence/measurements.md`](evidence/measurements.md#the-groves-build)).
- **The density capacity's invariants.** The capacity record's key excludes density and checks that the grove is the attached one and has free slots; `hier.nLeaf` and the ordinary key describe the active population. The faithful cast frame follows the active leaves: plan bounds scan their double positions plus the wood, and `faith.hMin`/`hMax` start from the twig tips and widen only to active inner leaves, while the layer bins and the fill's `binH` stay the fixed skeleton's. The live morph's leaf budget counts the exact larger prefix, the marginal leaf included, beside the previous conservative estimate, so a source with no leaves cannot slip past it. The bend is republished and the replaced regrow's activity hint (`hier.maxV`) cleared as a regrow would. An interruption or reversal reuses a sufficient capacity or builds a larger one once. The path is independent of every autumn `FEAT_` flag, so a summer bundle may cut them all.

- **Leaf travel's carriers move on the GPU.** The route keeps each carrier's two ends static, as five vec4 a side (the faithful record, the height slot holding a layered end's layer fraction, then fade, pivot weight and outline row) and the pair's liveness and place in the patch field, uploaded once (`carrierRecords`). Once a frame a transform-feedback pass (`VS_LEAF_CARRY`, nothing drawn) evaluates each end's leaf at its own wind from that end's cluster textures, which its wind already publishes for its bake, carries it, and writes the floats `moveLeaves` wrote into the buffer the stamp (`VS_LEAF_TRAVEL`, as grove travel's) draws from for every sun sample: a carrier is moved once a frame, not once per corner and sample. `moveLeaves` and `movePatchLeaves` stay as the reference that pass is held to, float by float (`test-gl/leaf-travel.mjs`), and as the patch field's ends. A shared program may name the outputs such a pass writes (`sharedProgram`'s third argument), linked with them. The map is framed on the CPU before the pass, from the carriers' own plan points less their flutter, which moves no centre, and their drift (`framePoints`: one twig and limb turn per clump, a leaf on older wood's own smaller twig turn, its tree's sway at its height), lerped at each carrier's progress and boxed (`carrierBox`), widened by the drift's largest orbit, and padded by the largest carrier at any flutter, bounded once a route (`carrierSize`): a carrier between a foreshortened end and an open one is longer than either end's leaf, and its longest side peaks with each end's foreshortening at one of its limits, so the four corners are taken along the trip. `leaf-travel.test.js` holds that the frame contains every carrier `moveLeaves` and `movePatchLeaves` place and is their box but for that orbit, and that no carrier is larger than the pad's bound.
- **Season travel's pivot weights.** The route puts the grove's whole record in the faithful buffer, fallen leaves included, so it uploads the record's pivot weights (`season.pivot`) beside it, and under `twig_joints` its joints (`season.run`): a re-season leaves only the survivors' weights there, and a draw that reads an instanced attribute past its buffer's end is refused by the browser, with no leaf cast. The moving cast is drawn by `VS_SEASON_TRAVEL` and reads no weight ([`model/canopy.md`](model/canopy.md#approximations-and-limits)); each resting end is cast by the shader it rests on. `season-travel.test.js` holds both on a GL that refuses what a browser refuses, since a software rasteriser draws the short read.
- **The litter flights** accumulate optical depth and reflected-light moments in **two RGBA16F eye targets** at up to twice the canvas dimensions. The final read averages four transmittances, not four optical depths.
- **The scene dissolve** renders both scenes into canvas-sized **RGBA8** targets in one GL context. It decodes them by gamma 2.2, mixes, and re-encodes. Its outgoing scene is the look on screen, so it takes the engine's grove (the leaves, the faithful leaves and wood, the wood's table, the sky view's binned wood) instead of growing it again, and the engine grows only the incoming look's; the scene frees that grove when it is released. The routing suite holds the handover: the faithful leaves' buffer on screen when a dissolve starts lives on in the outgoing scene, and is gone once the dissolve ends.
- **Cleanup.** Every route releases its temporary scene and textures on completion, hard replacement, disposal and context loss. Its programs are the context's table's, held by the host engine (above), and stay linked for the next run.

## The signatures that decide a re-bake

Several passes do not run on a schedule. Each frame they compare a numeric snapshot of their inputs and re-run only when it has moved. Each signature carries exactly the inputs that change a bake's output without some other bake running. A missing entry freezes a picture while its knob tweens. A spurious entry re-bakes every frame.

**The fill's signature** (`fillSig`, length `FILL_SIG_LEN` = 24, exported, and the engine sizes its array from it). It re-runs the fill alone when the sky or the sun moves and no bake does. Its slots, in order (`komorebi-bake.js`):

0. the sun's elevation, 1. its azimuth, 2. the turbidity (the sun's colour and the sky's);
3. the leaf albedo the fill pass reads (`fill_scatter`, on a floor camera), 4. the ray count, 5. the fill texture's resolution;
6. the layer count, 7. the canopy's base height, 8. its thickness, 9. its extent;
10. whether the cast is faithful, 11. the leaf's ballistic share (`leaf_diffuse`, through `ballisticK`): it changes what `S` is made of, and no bake runs when a MORPH key tweens;
12. whether the canopy wraps (the open box and the padded frame of a finite tree);
13. the edge law (`edge_area`): it changes what both `T_sky` and `S` are made of;
14. the receiver's cosine (`sun_cosine`) and 15. the air's loss (`sun_extinction`): live scales of the sun colour that `S` reads;
16. the park's shear (`park_throw`, 0 on a finite scene): it moves the beam's path the fill bakes along;
17. `ground_bounce`, the share of `B` the fill pass adds to `S`;
18–20. the ground's albedo, 21. `ambient_skylight`, 22. the carpet's bake count (a new carpet per regrow): what the ground's light is made of. Each is 0 (the carpet −1) while `ground_bounce` is 0;
23. the share of sunlight that survives the eclipse.

The skylight's level is otherwise not in it: `ambient_skylight` scales the fill where a receiver reads it, not where it is made; only the ground's light, which reads the open sky, is made of it.

**The faithful cast's snapshot** (`refreshFaith`). A still faithful cast compares a reusable snapshot before drawing:

- the source offsets and weights;
- the sun angles;
- the cloth plane;
- drift;
- the leaf-bake uniforms;
- the bake resolution;
- alongside it, checks on the diffuse split, the wood and the edge law.

A change re-casts once even with the wind off. Regenerating identical samples does not. Sample count alone cannot describe the source or its projection. The live-wood refresh re-casts when a radius, layer-height tween or `branch_tau` changes, including in still air. With wood off it does nothing, so a leaf crossfade never rewrites the incoming grove's faithful geometry from the outgoing skeleton.

**The carpet's signature** (`refreshLitter`, once per frame, before any target is bound). It re-bakes when any of these moves:

- the grove (a new value per regrow, a transition's morph included);
- the authored wind direction;
- `litter_age` and `litter_drift_m`;
- the phenology;
- the seed;
- the size or the frame;
- `leaf_wetness` (MORPH-class, so only the carpet re-bakes).

It never re-bakes for the live wind, the sun or the fill. It keys on the grove and the litter keys, not the pigment capacities. A re-bake does not sort or draw again what the clock did not move: a re-seasoned grove's list carries its drop order (`byDay`, not enumerable, read off `season.sched.byDay`, every leaf in `litterOrder`'s order, sorted once per schedule), and `litterInstances` keeps each landing (`newLitterCache`, per grove, keyed on the seed, the drift and the wind direction, checked against the leaf's own place), writing the instances straight into one typed buffer. Every route that grows a grove calls it, including a context restore and an editor slider. The harness measures `passes` at 1 after two dozen frames.

**The grove's structural key.** It is every param `buildGrove` reads besides the season set, plus `faithfulOn()` (`GROVE_READS`). The list was derived by grepping the grove, and a test greps again. A key mismatch regrows; a change only in `SEASON_KEYS` re-seasons. Every season key's row in the panel asks for the `'season'` scope, so a slider on any of them is that re-season after the one build that makes the record; `reseason.test.js` holds the rows to `SEASON_KEYS` and each move to a fresh build. The other stages (the source's cut, the bakes, the fill, the carpet) re-run on signatures and on what a frame uploads, which no list in the source says whole, so their rows are held by asking the engine: `nix run .#rows` (`test-gl/rows.mjs`) moves every row on a running engine by its own scope, on the GPU, holds the frame to a look born with the value, and tries each cheaper scope in its place. A row found asking for more is read against the source before it is narrowed; the motion's rows cannot be judged on a still scene. The density-capacity record has its own key, which excludes density and checks buffer ownership and available slots.

**The held-leaf inset** (editor only). A change of leaf, size or (for an outline) aspect regrows the maze. The vein share re-rasterises the masks. Season and pigments only recolour. A regrow or re-raster waits until its inputs have been still for 250 ms.

## Numerical discipline

The piece's preservation and determinism contracts are executed by equality in pixels ([`contracts/preservation.md`](contracts/preservation.md), [`contracts/determinism.md`](contracts/determinism.md)). That makes floating point a design input. These are the traps the code is built around.

- **GLSL matrices are column-major.** The joint rotations are written `mat2(c,s,-s,c)` in both leaf shaders and in the CPU wood, the same counterclockwise rotation. Reverse that constructor and the foliage separates from its wood under wind. A still frame cannot show the mistake, so only motion exposes the sign. The leaf's own angle is the same trap the other way: the outline uses a clockwise rest-angle basis while the joint bends are counterclockwise, so the shaders write `angle − limb bend − twig bend`.
- **A divide by a uniform is not a divide by a literal.** A divide by a uniform may compile to a multiply by a reciprocal (about 2.5 ULP), where a divide by a literal may be an exact multiply. So `GLSL_LEAF_Q` keeps its literal `/8.0` line, and a uniform branch (`if(uLeafRows > 0.0)`) overrides it only for a varied grove. The vertex side can take the uniform: a highp `*` is correctly rounded, and x·32 is a power-of-two scaling of an exact fraction, so `fract(iC.w)*uLeafIdFrac` at 32 is the same IEEE bits as the literal it replaced.
- **Zero terms that vanish exactly.** With `edge_area` on at `k = 0`, every reader takes `texelMix`, and `exp(-tbar - 0.0*c/a)` is `exp(-tbar)` bit for bit, so `T_b = T`. Likewise `sky_scatter = 0` adds an exact zero to the transmission term, which IEEE 754 guarantees. The wet step at `leaf_wetness` 0 gives `S_w = 1` and `F_w = F` exactly, checked with `Object.is` against the dry evaluation.
- **Angles are made in float64 on the CPU.** GLSL ES promises only about 2⁻¹¹ absolute error from `sin` and `cos`. A fill ray's plan shift is `tanθ·h`, tens of metres near the horizon, so a few 10⁻⁴ of angle is centimetres on the floor, more than a leaf's edge. The fill's unit vectors `(cos φ_k, sin φ_k)` and the sixteen tile rotations are computed in float64 and uploaded. The shader rotates, shifts by cos²θ and takes one `sqrt`. A first shader that computed `cos φ` itself missed its CPU reference by 3·10⁻³ to 9·10⁻³.
- **Identities that make an off state exact.** At aspect 1, `Math.sqrt(1)` is exactly 1 and `x/1` is `x`, so an outline's `A` and `B0` keep their old bits. The ellipse's quad is `aCorner·1 + 0`, the same bits.
- **Float sums do not undo.** `(x + ε) − ε ≠ x` in float, so the drop gate opens one `DROP_EPS` early on purpose. An early open is free, because `retention` returns exactly 1.
- **Pin digests rather than re-deriving them from buffers.** Positions come back from the buffers through float32, and re-ranking from them re-orders a few dozen leaves in ten thousand. So `drop.test.js` freezes a digest of every leaf's τ instead of recomputing it from the buffer. Likewise the density-capacity path never divides a fade out of float32 data, and keeps the literal marginal-leaf × marginal-tree multiplication.
- **Stable inverses.** `kmReflect(X) = 1/(1 + X + √(X² + 2X))` is the stable form. The textbook `1 + X − √(X² + 2X)` is NaN at `R = 0` and cancels badly below `R ≈ 1e-4`.
- **Writes past the end of a `Float64Array` are silent.** An out-of-range index write is dropped without error. A signature array sized by hand and shorter than its writer would leave a slot permanently at its old value, compared against a fresh one that never lands, and the fill would re-bake every frame. So `FILL_SIG_LEN` is one exported number, and the engine sizes its array from it.
- **The `FEAT_` constants are declared verbatim** as `const FEAT_X = true;` in each module that guards a tier. The build substitutes that exact text and throws on a module that uses a flag it does not declare. Without that, a module that forgot the declaration would keep its tier while the build reported it cut.
- **The orphan sweep runs to a fixpoint.** After every other cut, a top-level `const GLSL_|VS_|FS_ = ` literal that nothing references except its declaration and the import/export lists is deleted, together with its list entries. The sweep repeats until nothing more goes. It exists because a minifier keeps an unreferenced template literal that contains a `${}`. Before the sweep, a floor-only bundle carried the cut sky camera's `uSkyScatter` four times. The minifier folds `false ? A : B` only after the sweep has counted A's references.
- **Half-float tolerances are stated, not assumed.** The fill check holds the shader to its reference within one half-float ULP. The fill check with the split on holds within 1.2·10⁻⁴. The sky check's worst error is 1.6·10⁻⁴ against a tolerance of 10⁻³. In each case a wrong ray, height, weight or sun path is orders of magnitude outside the tolerance.

## The editor and the player

The editor is a tool for exploring the model, not part of it: nothing here reaches a look's frame, a bundle or the engine. `index.html` is its shell and `editor/editor.js` its body; the map names the pure modules beside it.

**Two surfaces, and the sidebar's depths.** The mode ladder runs from a zen strip (the default, which fades after stillness) to the sidebar, the sliders icon climbing and ✕ coming back down. The sidebar has three depths, one icon each in its header, the one it is on lit and remembered: *simple*, its dials; *advanced*, every setting, area by area; and on a desktop the *workspace*, where the panel docks under the picture. Neither surface names its mode. After "feel" the active surface slides in, on a touch screen as on a desktop. **D** toggles it (in zen it wakes or fades the strip); **F**, or a double-click on the picture with a mouse, toggles fullscreen. With a mouse, a **click** on the picture brings the sidebar back, at either depth, from wherever it has gone (slid away, or faded from the cursor), whole until the cursor has been over it; with it whole, a click sends it away as D does, and the next brings it back (in zen the press itself wakes the strip). A click is one that moves under 4 px before release (past that it is the camera's drag), and it waits out a double-click, which is fullscreen alone. On touch there is no keyboard: a **tap** on the picture toggles the surface as D does, and yields to a swipe once the finger passes a 12 px deadzone. The first arrival on a touch screen shows the two gestures once, in the key-hint line. While a finger holds a slider on either surface, or a mouse moves one it holds, everything but that slider's row fades out over about half a second, the panel's glass with it, so the picture shows, and fades back on release; a click on a track alone, or an arrow key, leaves the surface be. The docked panel clears for a finger only: with a mouse it stands beside the picture in the workspace.

It draws the grove's own skeleton (`hier.segments`, tapered quads, solid behind the leaves and faint over them) and a blob per leaf, placed by the grove's own `placeLeaf` over the grove's draw order, as a translucent haze whose per-leaf opacity falls as `leaves_per_cluster × foliage_density` climbs, a different green per tree, in a slowly turning three-quarter view with a wind arrow and a ground grid. A dropped leaf leaves it: it reads `hier.leafW`, the retained weight by (twig, slot), which is null at the abscission gate. It is projected on the CPU into a scissored corner, so it costs nothing unless shown. **Approximation:** its sway is a height-weighted downwind lean plus the first tree's trunk drift, for every tree, not the bake's per-joint motion and not each tree's own trunk, so it leans a little harder than the cast moves and its trees lean together.

**The workspace** (`W`, or the sidebar's *workspace* icon; desktop only). An IDE's layout for working on a tree: the picture becomes a viewer at the top left with nothing over it, the tree pane (`tree-pane.js`) stands beside it, and the panel docks in the band below, its rows flowing in columns across the screen and scrolling sideways; the MIDImix console (**M**), while it is up, docks at the band's right end beside them, and its caption rides the viewer. While it is up, **D** leaves the docked panel where it is, the sun's inset is not drawn, and a counter in the viewer's top right, on the same glass as the panels so it reads over any sky, always shows the frame rate and the resolution auto-quality draws at. It sticks across reloads like the mode. The engine sizes its backing store from the canvas's box every frame, so the smaller viewer is all the change the picture needs. **The tree pane** draws the grove's own wood and leaves (the leaves the tree inset draws, the wood at the pipe model's width) under one of two cameras, flicked with a click: *side*, from the ground and level against a sky, the leaves darker with depth, the view a photograph of a tree is taken from; and *turn*, the tree inset's turntable from 24° above over a ground grid. Its scale comes from the grove's bounds, so the views share one size. It is drawn as discs with a depth test on a WebGL2 context of its own; the discs are laid out once per grove, after the grove has stood still for a quarter second, and a frame is one draw of them. The tree stands still: no wind. **The playlist pane** (`playlist-pane.js`) stands in the tree pane's place, one of two tabs (*tree*, *playlist*) over its top; which is up sticks across reloads, and the tree is not drawn while the list is. While it is up it is the one home of looks and playlists: the docked panel's look and playlist controls move into it, the playlist leading (the story line that opens the stories, ✎ to rename a playlist of yours, + for a new one, its display), then the look (‹ name ›, its chip, the chips that put it into a playlist of yours or take it out, arboretum's status line, *arrives by*), so none is left in the panel below and none is a copy; the *tree* tab, or leaving the workspace, puts them back in their place. Under them it lists every entry of the active list, the one you are on marked, and a click on a name goes to that look as the arrows do. On an arboretum playlist each item shows its hold (`dwell_s`), its arrival (`crossfade_s`) and its route (*morph* or *fade*). On a playlist of yours these are edited in place; a drag on an item's grip moves it, the selection staying on the look it was on; an × takes an item out (the preset stays in arboretum), and taking out the look on screen goes on to the item that took its place, so what is selected is always what is shown; and a picker at the foot adds one of your looks (marking those already in it) or a ★ not yet in arboretum (sent up first) at the end, without leaving the playlist. A built-in goes into a playlist only once it is changed and saved. A list with no order of yours to change (your looks, a shipped playlist, uncategorized, someone else's playlist) has no grip, no × and no picker; so without arboretum, on `nix run .#dev` or a fork, the pane switches lists and saves but changes no playlist. Each write is one items write, from a fresh copy of the playlist, of that one change; the owner's unavailable items keep their places, and a value arboretum refuses is said in the status line and the stored one comes back.

**The held leaf** (`L`, bottom-left) is [`model/leaf.md`](model/leaf.md#the-held-leaf)'s. `[` and `]` walk one ring over every leaf the grove hangs, cluster by cluster, wrapping at both ends, and a click enlarges it. It carries a 1 cm bar, the address `j·k`, the outline variant and s, a and b; with a per-tree knob up, the tree it hangs on with that tree's lead Δ and depth c, drawn from the seed the picture was made with, so it recolours with those sliders like the pigments. **What a look costs** is measured off the page, by `nix run .#cost` (`test-gl/cost.mjs`): a look, or a look against a change to it, on Chrome on this machine's GPU at 1080p with auto-quality off, A and B alternated over runs. The headline is the whole frame (each closed by a one-pixel read, no vsync) and the time to regrow the grove; the timer queries' per-pass figures come second, because on Metal they read more than the frame takes. The editor once carried a profiler that cut and proposed lighter variants of a look on an A/B wipe; it went, and its findings stay in [`evidence/measurements.md`](evidence/measurements.md#the-profilers-findings).

**The macro bus** (`macros.js`). The sidebar's and the strip's controls are macros, not parameters: one input `t ∈ [0, 1]` drives an authored recipe through `createBus`, `set(key, t)` in and a partial parameter set out, so MIDI or audio could drive the same keys. Every stop is lifted from a shipped look; numbers interpolate piecewise-linearly between stops, and strings and booleans snap to the nearer. Each macro declares a **probe**, a parameter strictly monotone across its stops, which the bus inverts to seat the thumb on the current look. A macro is gated to the cameras where its recipe is honest: `floor` (haze, ground, season, grove) needs the floor receiver and no sky view, `cast` (prism) any camera but the sky view. What a macro may never write is [`contracts/gates-and-rungs.md`](contracts/gates-and-rungs.md)'s.

**The season macro.** Its stops, `t` against `phenology`: `memories` 0 and 0.15, `morning 1` 0.35 and 0.40, `afternoon 4` 0.55 and 0.50, the last green day 0.62 and 0.60 (`turn_start`; no look), `montebello` 1 and 0.90. At every stop the capacities are `montebello`'s: `anthocyanin` 0.4, `tannin` 0.2, `wall_fraction` 0.2, `turn_exposure` 1, `leaf_drop` 1. It declares `tween: 0.8` s: `set` stores a target, and the frame clock's `tick(dt)` eases the macro's own value toward it by one pole, `x += (target − x)(1 − e^(−dt/τ))`, monotone, never overshooting, and composing across any split of the same elapsed time. Each tick applies the recipe at scope `'season'` once, and only when it changed; within 0.002 of the target it applies the stop's exact parameters and idles; loading a look cancels it. The step clamp (`TWEEN_STEP`) is [`model/season.md`](model/season.md#a-season-played-live)'s.

**The cost gate.** The editor times every season apply and keeps a moving average of it (`tweenGateStep`): when one costs over 12 ms the next waits `cost/0.30` ms of wall time, while the ease keeps running on the clock, so the catch-up is a bigger step and not a stall; once the average passes 50 ms the drag falls back to one exact apply on release. A one-off build of the re-season record is not measured, or it would latch the fallback for the whole drag; a build that follows a build, the spring half where every tick regrows, is.

**The MIDImix** (`midi.js`, editor only, Web MIDI). An AKAI MIDImix drives the same controls the hand does: the try-out dials (home is the look's own value), the macro bus, a few panel rows through the dials' own landing, and the arrows' step for the bank buttons; the engine never knows. The factory map is the wire: per strip three knobs and a fader as CCs, the master fader as CC 62, the buttons as notes, and a note sent back to a button lights it. Two layers share the desk, *general* (light, sun, wind, canopy, season, camera, floor, transition time) and *colour* (ground, leaf, shade, cloth, frame edge, foliage glow, the fall's pigments with the season under them, the fallen leaves); REC ARM 7 flips them and is lit on colour. Every colour control is a quantity a look already authors, home-relative or across its row's range, never a grade on the picture. The master fader is brightness on both. A physical fader has a place the look does not, so **takeover** decides the first touch: *catch* (the default) moves nothing until the hand passes the look's value, then follows exactly; *glide* eases toward the hand; *jump* takes the hand's place. Every write lands at most once a frame, and none while a transition runs. Loading a look or flipping the layer lets every catch go. MUTE returns its strip to the look's values and is lit while the strip has moved; a control a look cannot use says why. **M** or REC ARM 2 shows the console: the layer, the device, the takeover, the last message, and every strip's value against its home.

**The remote control** (`remote.js`, editor only; arboretum's `/arboretum/remote` and `arboretum/src/remote.ts`). A phone drives an editor that is showing somewhere else, a projector on the wall, both signed in to arboretum as the same person. *Remote control* in Settings turns it on for the device; while it is on and signed in, the editor is a **screen** in the person's **room** on arboretum, a Durable Object that relays and keeps nothing. The phone's page lists the screens in the room by browser and system, picks the one it picked before or the only one there is, and is sent that screen's **board**: the look's name, chip and arboretum's last word on a save; ‹ › and ▶/■; *save*, *save as new*, *as it was*, *new leaves*; the dials, the look's own lead first as the playful sidebar has them and every other dial after, each with its home marked and dimmed where the look cannot use it; the "more" macros (haze, sparkle, trees, the wind's two axes) and the transition's time; the playlists with + and ✎, the playlist's display, and the active list's entries, which on a playlist of yours carry the hold, the arrival, the route, ↑ ↓ and ×, with a picker that adds a look; and every row of the panel by area, a row the look cannot use hidden as it is in the panel. What the phone sends lands on the function the editor's own control calls (the dial's write and its release, the bus, the panel row, the species, the step, the playlist pane's writes one after another), after the editor checks it against the board it sent: a name it does not have is dropped, a number held to its control's range. A slider on the phone sends at most every 50 ms and its release at once; the screen sends what changed at most every 100 ms while a phone is there, and nothing otherwise. A screen's id lives in its tab, so a reload comes back as the same screen and the phone stays on it; the projector says when a phone arrives and leaves. The phone renders nothing: it carries no engine and no look, only the board.

**Lists, play and links.** What the dropdown lists, and what the arrows, the ‹ › and the swipe walk, is the active list. A step by hand walks on from one list into the next: past a list's last look to the first look of the next list that has one, and back past its first look to the last look of the one before. The walk (`walk` in `playlists.js`) is the shipped playlists in their order, *park story* first, then every other list the dropdown holds in the dropdown's order, and *experiments*, the last shipped playlist, last of all; its two ends hold, so back from *park story*'s first look and on from *experiments*' last stay where they are. Play never leaves its list: it goes round it, from its last look to its first, and a list stepped into by hand while playing plays round that one. Its rules are `playlists.js`'s; arboretum's three tiers (local always, read from any origin, the session only where arboretum answers and you are signed in) are set out at the head of `arboretum.js`. The lists are the shipped playlists (`PLAYLISTS` in `presets.js`: the story, *park story*, then *komorebi*, *shadows*, *rainbow* and *experiments*), your looks (the ★ looks, listed once there is one; signed in, *on this browser*, the ★ looks not yet in arboretum) and arboretum's playlists. The stories list them in one order, the walk's: the shipped playlists, *park story* first, then the person's own (signed in: *uncategorized*, their folders in arboretum's order, others' playlists, *on this browser*; signed out: your looks, then arboretum's playlists), and *experiments* last. A shipped playlist and an arboretum playlist play, because they carry times (a shipped item's own, else its playlist's crossfade, else `ITEM_DEFAULTS`: held 30 s, arriving over 4 s by the automatic route; *park story* arrives over 2 s); your looks do not. The panel's fade row shows the crossfade the active list brings; set by hand (the row, the advanced depth's, the MIDImix, the remote), it overrides that list's crossfades until another list is chosen, and on your looks it is the only time there is. Each look is held for its dwell, then the next arrives over its own crossfade, by the automatic route or as a fade, which each item of a playlist of yours chooses on a *morph* / *fade* row in the panel (the item's, not the look's; the row is absent where there is no such item), and the dwell starts when a look has **finished arriving**, so a long crossfade never eats the time a look is meant to be seen. ▶ (the sidebar's, the MIDImix's, the remote's) steps to the next look at once, never waiting out the one it was pressed on; a list a link opens playing shows its first look first, with no fade in, for its dwell. Any edit of the look stops play; a step by hand restarts the dwell. Nothing plays by itself: a list plays once ▶ starts it, or when a link to it opens it. A first visit lands on the story's first look, which "feel" fades into; a later visit opens where you left off. Signed in, nothing on the story asks arboretum anything until every setting is first shown (the advanced depth or the workspace) or an arboretum playlist is chosen. A look brought in by a link refreshes in place the copy already here from the same preset, and never one holding an edit not yet sent up (it lands beside it); the hash is cleared once the look has landed, and a failed link says why in the key-hint line. *Copy JSON* and *paste JSON* move a whole look as text.

**Saving.** *Save* keeps the look on screen and *save as new* (the remote's; the editor's own is *save* alone) always keeps a new one, asking a name of its own; either way the editor ends on the saved look, in the list that holds it, and says where that is. Signed in to arboretum: *save* on a look of yours is a new version of it, in place; on someone else's item in a playlist of yours it is your own new preset in that item's place; *save as new* in a playlist of yours is a new preset right after the item you are on (at the end on none). Anywhere you cannot write (a shipped playlist, someone else's playlist), either is a new preset in uncategorized, and the editor goes there; in uncategorized, *save* is a new version and *save as new* a new preset there. Signed out, playlists are arboretum's and read here only: a save is a ★ in this browser, in your looks, where the editor goes, and a line under the look's chip says so, and, from a playlist, that adding a look to one needs arboretum. *Save as new* never quietly replaces a ★ of the same name. Deleting the ★ you are on goes to the first look of your looks, or to the story once there is none.

**The player.** `player.html` is viewer-only: no panel, and no input but a pointer that hides after 3 s at rest. ### Session settings

The [session contract](contracts/sessions.md) owns the rules. `komorebi-session.js` supplies the pure `resolveSession(settings, environment)`, `resolveParams(look, resolvedSession)` and `authoredLook(look)` exports. `create(canvas, {params, session, environment})` opts into the policy; omitting `session` retains the flat-params path. The engine exposes `setSession(settings, environment)`, `authored`, `captureLook()` and `setLookRequest(key, value, scope)` (undefined removes a fidelity opinion; with a rebuild scope the request lands in place through that scope's rebuild, as the editor's rows apply it, and without one, or during a route, it swaps the whole look). Transition targets resolve before classification, and queued arrivals resolve again under the latest policy. Structural settings wait for arrival; runtime choices apply immediately. Context restoration uses the same policy.

The fidelity keys are `sample_count`, `tex_resolution`, `bake_resolution`, `fill_directions`, `fill_resolution` and `litter_resolution`. The three playback keys are `auto_quality`, `adaptive_motion` and `adaptive_idle_fps`. Layer count and tone mapping remain artistic controls. Calling `setSession` on a flat-params engine retains live art edits and omitted fidelity requests. Refused inputs leave authored data intact. Even a sample request below the governor's usual floor remains an upper bound in a session.

**Provisional shipped ceilings**, in that fidelity-key order: compact `(24, 1024, 768, 8, 128, 512)`, balanced `(32, 1024, 1024, 16, 256, 1024)`, high `(48, 4096, 2048, 32, 512, 2048)`, export `(48, 4096, 4096, 64, 512, 2048)`. Automatic quality selection uses phone user-agent identification, not coarse-pointer input alone. Hardware texture limits cap the resolutions. Auto-quality starts on, with idle cadence 30 available for adaptive rendering. Automatic FPS follows the [startup cadence rule](contracts/sessions.md#rendering): `makeFpsProbe` counts full-rate frame intervals while Automatic is selected and no explicit adaptive override exists. The engine excludes hidden-tab intervals, latches a low-cadence result across look/presentation changes, and reports it in Settings. Switching away from automatic policy discards that observation. Manual profiles retain device playback defaults (adaptive on for phones, off elsewhere); explicit overrides win in every mode. Quality ceilings need hardware calibration; they do not guarantee frame cadence.

`editor-settings.js` builds one modal Settings panel, behind the cog in the sidebar's header and the docked panel's; the zen strip, on a desktop and in its touch tabs, has no Settings button. Preferences are versioned under `komorebi.editor.session`; absent playback/ceiling overrides follow the profile, and explicit false is retained. A setting that follows the profile says what the profile gives it now, *follow profile (32)*, and *automatic* the profile it picked, *automatic (balanced)*, both kept current with the status line. Presentation is follow-playlist, screen or projector. The account row reuses Arboretum's existing passkey page and connection checks. Session edits neither stop a playlist nor mark a look edited. Authored data drives save/copy/upload.

Playlist `presentation` is an optional shipped identifier. Arboretum generates the identifiers from the engine beside it (`arboretum/scripts/engine.mjs`) and guards presentation PATCHes with the common playlist revision. Local caches and mirrors preserve the field. The editor and Arboretum players use session-aware playback; independent site previews do not read editor preferences.

`render-video.mjs --session-json <file>` selects a fixed session through the exported engine's own resolver, defaults quality to export, and refuses `--set` in the same invocation. `--ss` remains capture configuration. The run key and manifest freeze the requested settings, resolved profile definition, authored inputs and all effective endpoints. Scheduling, tiny preroll, serial and parallel capture receive the same concrete endpoints; both governors remain forced off. Legacy exports without a session file retain their override path. The render service accepts `session: {quality?, presentation?}` with optional top-level `ss`; legacy `quality` jobs keep their previous meaning and cannot be combined with session.

`render-video.mjs` renders a playlist with the routes the engine picks, structural ones included: before the render it asks the exported engine, once per fade of the loop and from rest on the outgoing look at its own sizes, which route the fade takes and how long its clock runs (`video.html` `routeClocks`), and lays the timeline out from the answers, so each look's dwell counts from its real landing. A playlist with a structural fade renders with `--jobs 1` only: the tiny pass integrates at its own sizes and would not take the full-size engine's route.

`reseason.test.js` ends with two timing reports that assert nothing; they run only with `MEASURE_RESEASON=1` (`MEASURE_RESEASON=1 nix run .#test -- test/reseason.test.js`) and are reported as skipped otherwise.

CPU policy/lifecycle tests are `sessions.test.js`, `sessions-engine.test.js` and `export-session.test.js`. `test-gl/sessions.mjs` checks editor persistence/save behavior and real WebGL native arrival; it is separate from the full pixel suite. Bundles retain the edge-law tier needed by default screen sessions unless an explicit feature override cuts it.

## The harness

Two tiers. The **unit tests** (`*.test.js` in `test/`, run under `bun test`) hold the pure laws, plus the wiring over a stub GL. The **pixel harness** (`test-gl/`, run by `test-gl/run.js` through `test-gl/harness.html`, with helpers in `harness-lib.mjs`) renders real frames in headless Chromium on WebGL2 via SwiftShader. Under frozen motion its captures are stable to the byte, so the assertion is equality rather than a tolerance. Renders are evidence, not source.

### Pixel harness suites (`nix run .#pixels`)

| Suite or row kind | What it proves |
|---|---|
| **Smoke** | every shipped look creates, renders a non-degenerate frame and raises no GL error; a PNG per look under `test-gl/out/` |
| **Gate invariants** (equality rows) | a gated feature's off state reproduces the previous frame in pixels: a floor look ignores the whole fabric family, a zero gate ignores its geometry, zero equals absent |
| **Live rows** (`differ`) | the two frames must *not* match, proving that the gate is a real switch and that the equality rows beside it are not passing on a dead feature |
| **Pins** | one look's own hash, written down from the engine *before* a change that touches no gate (for example, moving the sky view's wood to its own texture). An a == b row can survive a change that moves both sides; a pin cannot |
| **Energy rows** (`lit`) | the frames differ *and* the split frame's mean level lies between bounds; a frame that threw its diffuse light away sits below them |
| **Continuity rows** (`near`) | a leaf count stepped from none to 0.005 of a leaf moves the frame by a hair (the marginal fade) |
| **Determinism** | two independently created engines under frozen motion give equal frames: no sampling RNG, measured |
| **Fill check** (`--fill`) | the engine bakes a real fill; the harness reads back the layers it read and the `T_sky`/`S` it wrote, rebuilds them at sampled texels from `komorebi-fill.js` (bilinear taps through the fill's own domain, the bake's heights, atmosphere and beam sun path) and compares within one half-float ULP; also run with the split on, emission against coverage read back out of alpha |
| **Gate crossed on a running engine** | what is allocated at each step, and that shutting the gate again restores the old frame exactly |
| **Live-change suite** | a knob assigned on a running engine gives the frame an engine born with it gives (the fill re-bakes, the faithful cast re-casts) |
| **Bookkeeping rows** (`__fillCheck`'s `energy`) | on the real baked layers: what the leaves emit, what the hemisphere sends down, what the beam gives up, what the fill texture holds. The endless park is held to its closure and the bottom layer's identity, the beam's deficit to the clumping band, a finite tree to its padded frame's share and the glow's decay at the frame edge. These rows were red on the engine before the wrap, the frame and the one-sun rule |
| **Sky check** (`--sky`; `SKY_CHECKS`, `__skyCheck`) | a program compiled from exactly the engine's snippets (`GLSL_LAYER_FIELD`, `GLSL_WOOD_FIELD`, `GLSL_SKY_RAY`) runs 1024 fixed eye rays with `readWood` true on the layers and R16F wood the engine baked, and holds `T`, `T_src` and the glow to `skyRayRef` at `d` 0, 0.5 and 0.95 on `canopy 1`–`4`; the rows also count what they measured |
| **Edge rows** (`--edge`) | the lantern's rim, the beam's halo and the faithful stamp, each measured on the shader the engine compiles and the layers it baked; `edge_area` has rows in each suite |
| **Litter rows** | the whole family armed behind a shut gate in a frame the carpet would bite (zero equals absent at phenology 0.9 with `leaf_drop` 1); `differ` on both floor paths, with the fill open; curtain, tent and sky view unchanged with the gate open |
| **Carpet check** (`__litterCheck`, `--gate litter`) | the baked RGBA8 carpet read back and held to a CPU painting of the same stamps in drop order, with the reverse order as the yardstick; a sparse carpet to its closed forms; `passes` at 1 |
| **Stamp check** | a direct draw of the stamp shader: layering (`src + dst·(1 − a)` exactly), the blend, sub-texel area, the rim |
| **Context-loss rows** | a look with the fill open, and one with the carpet, since their programs, textures and buffers exist only while a look opens those tiers (`montebello` opens both); restoration rebuilds them |
| **Transition routing** | each tier driven to completion; logic only |
| **Eyes mode** (`--look "<look>" key=value …`) | a look rendered with overrides, re-baked first, written to `out/`; not a suite, and asserts nothing |

`--only <substring …>` runs rows whose suite, name or look matches a substring. Use `--list [substring …]` to see the matching rows without rendering. If `--only` matches nothing, it reports an error.

`--gate [substring …]` runs only the gate rows whose name matches. It is the fast loop for adding a gate. `--fill`, `--sky` and `--edge` run their suites alone.

### Route drivers

`test-gl/viewpoint.mjs`, `leaf-travel.mjs`, `season-travel.mjs`, `litter-rise.mjs`, `litter-fall.mjs`, `shadow-rise.mjs`, `shadow-fall.mjs` and `grove-travel.mjs` drive one travelling route each on WebGL. Between them they cover:

- native endpoint pixels and moving landings;
- reversal and queued selections;
- wind, drift and adaptive clocks, and residual springs;
- the reduced-quality midpoint, resize and cancellation;
- hard replacement, resource release and context recovery.

Most take `--render` to capture the authored pair. What each route promises is in [`contracts/transitions.md`](contracts/transitions.md).

[--out f.json]` | not a proof: a dappled-light video (a render or a phone clip) read as JSON: the light patches (blobs of a difference of Gaussians that stand out from their own surroundings) and their clustering, Moran's I, the spatial spectrum, the brightness tempo, the optical flow, and how the pattern scrambles and comes back ([`evidence/measurements.md`](evidence/measurements.md#the-floor-pattern)) |
| **Shader validation** | `node glslcheck.mjs` | GLSL literals and variants compile under `glslangValidator`, including transport and tree fragments from the assembled player and embeds |
| **Video exporter** (`render-video.mjs` and its siblings) | `nix run .#video -- …`; tests via `node --test test-gl/video.test.mjs` and the other test files beside it, each naming its run command in its header | its own tests: downscale, frame pairing, run key and refusals, playlist timeline, parallel claims; GPU checks are separate files; see the map |

Pattern measures use the constant frame rate of the filtered output. JSON records the effective sampling rates and uses `null` when a measurement is undefined, including direction with no motion and spatial correlation with no contrast.

Playlist videos use the same transition timing as the editor. A checkpoint is saved after the new look arrives; if a render resumes partway through a fade, it replays from the last settled look.

### Running and what stays untracked

- **Unit tests:** `bun test` (the old spec's word; the exact devShell invocation is not recorded).
- **Pixels:** `nix run .#pixels`, with a suite flag where wanted. The first run on a machine needs `cd test-gl && npm install && npx playwright install chromium`. Playwright's Chromium sits outside nix on purpose, because it pins its own build. The video exporter's Playwright is pinned to the version of the Nix Chromium it renders with.
- **Untracked:** PNGs, everything under `test-gl/out/` (review folders included) and `node_modules/`.

## Build and bundles

**One definition of a build.** `embed-build.mjs` writes both bundles:

- `nix run .#build` keeps every shipped look and writes `dist/komorebi.player.min.js`;
- `nix run .#embed -- '<look>'…` keeps the named looks and writes `dist/komorebi.embed.min.js`.

The functions are exported, and the command line runs only when the file is the entry script (`bundle.test.js`, `features.test.js`). The assembled tree keeps the repository's layout, so every import in it resolves as it does here and a test names a module of it by its path (`engine/transport/komorebi-transport.js`). Every cut is read from a table, never decided by hand.

**Camera pruning.** `cameraFor()` reads the kept looks and names the cameras they select. `CAMERAS`, `TRANSPORT_GROUPS`, `GROUP_UPLOAD_KEYS` and the per-frame `GROUP_UPLOAD` are pruned to that set, keeping the three-halves agreement `registry.test.js` guards. An unreachable camera takes its GLSL, its uniform groups and its upload with it, and the orphan sweep removes its shader strings. Only the experimental looks select a camera other than the floor, so the player bundle carries the floor camera alone.

**The feature registry and the four-way cut.** The fall tiers are interleaved in the floor program and the grove, so no table cut sheds them. They are cut by a registry derived per look, the way the camera is. `FEATURES` and `featuresFor(P)` in `komorebi-params.js` say what opens each tier, and the build keeps the union over its looks:

| Tier | Opened when |
|---|---|
| `fill` | `canopy_fill > 0` |
| `leafDiffuse` | `leaf_diffuse > 0`, or `edge_area` on (its uniform is its own `beam` group) |
| `pigment` | `senescing` |
| `exposure` | the exposure pass runs (`ordered`) |
| `drop` | leaves are dropping |
| `litter` | `litter > 0` and leaves are dropping |

The predicates are those of `komorebi-season.js`, read by the grove and the registry alike, never restated. The dependency that is easy to miss: `ordered` is `lit || (dropping && !afterTurn && drop_exposure > 0)`. A look that drops by light therefore opens `exposure` without turning by it. A bundle that cut `exposure` for that look would drop its leaves in another order and paint a different tree, without saying so.

A cut is made four ways:

1. **`FEAT_` constants** (declared verbatim per module) are substituted. They turn the grove's arithmetic, the fill and carpet factories (`makeFill`, `makeLitter`) and the `ballisticK` calls into dead branches, whose text is then removed.
2. **The tier's uniform group** leaves every kept camera.
3. **GLSL lines tagged `// @feature <name>`** are dropped, each leaving the old expression as the whole body. `features.test.js` holds that any subset leaves every literal as balanced as it was, and that no assembled program names a cut group's uniform.
4. **The orphan sweep** deletes what the first three left unreferenced.

`--features a,b|all|none` overrides the derived set.

**The key-compaction gotcha.** The grove compacts dropped leaves out of both buffers by counting the leaves that went (`alive[i] = 0`). It used to ask `litter?.length`, which with the carpet cut and the drop kept would compact nothing, and the bake would carry thousands of zero-τ quads. The litter push is now its own guarded statement.

**The test that fails if a predicate is wrong** builds a grove with exactly the tiers a look does not open cut out. It requires every uploaded layer and faithful buffer to equal the whole grove's. Its reference holds the exposure gate open, so the test does not trust `ordered`. Either of these mutations turns it red:

- dropping the drop clause from `ordered`;
- reverting compaction to `litter?.length`.

**What else the build does.**

- It strips the comments from the shader literals. A template literal is opaque to a minifier, so the design notes were shipping to every visitor.
- It folds the editor tier off by substituting the `EDITOR` flag. A `--define KOMOREBI_EDITOR=false` never folded on its own: neither bun nor esbuild inlines `const EDITOR = <ternary>` into its use sites.
- It deliberately does **not** cut the faithful tier, the glow tier or the woody occluder. They are interleaved code rather than table data, so cutting them would mean editing the engine instead of reading it. They stay, gated off at runtime, and a later look that opens one still works.
- `leaf_variety` is a cost no cut sees. Its pass is interleaved in the grove's build and reaches `exposureGrid`, `exposureRank` and `treeGenotype`. A `FEATURES` tier opened by an outline together with `leaf_variety > 0` would be the way to cut it. None is built.

**The warning at the doors.** The build rewrites the engine's `BUILD` constant to the bundle's file name, its looks and the tiers it cut. At the three doors params come through (`create`, `setParams`, `transitionTo`), `cutWarnings` returns one message per cut tier the params open, and the engine `console.warn`s each once per engine, naming the `nix run .#embed` command that would build a bundle with the look. The raw modules cut nothing and pay nothing.

**What carries what.** The general player carries every fall tier, because `montebello` ships and opens all six. The lasting value is the per-page embed: `.github/workflows/pages.yml` builds the homepage's three-look bundle and publishes it beside the player. The proofs are in pixels:

- the player bundle renders every shipped look unchanged and keeps every tier;
- the homepage embed drops all six tiers and renders unchanged;
- combination builds (`--features <set>` over `memories`, `park 1` and `afternoon 7`, run with `--over` params that open the tier) pass for every set the registry derives;
- the two builds that must fail in pixels do: the drop's exposure rank cut under a look that needs it, and the fill cut under `canopy_fill` 1, which also prints the warning.

**Sizes** belong to evidence: what each tier costs, what the sweep and the pruning saved, and the bundles over time are in [`evidence/measurements.md`](evidence/measurements.md). `nix run .#build` prints the current size, and that size grows with every look added.
